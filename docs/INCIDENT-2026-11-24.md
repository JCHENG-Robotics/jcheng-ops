# 事故记录：2026-11-24 OOM → 用户态卡死

> 结论先行：一次约 4 GB 的 Python 进程触发全局 OOM，随后 sshd、网关、相机
> 启动服务一起失效；内核与网络仍然正常，所以所有只探网络的检查都显示“在线”。
> 机器人只能断电恢复。本仓库就是这次事故的产物。

| 项 | 结果 |

| 机器人可用性 | 约 09:20–09:53（≈33 分钟）不可操作，最后靠断电恢复 |

## 3. 根因

直接原因：**全局 OOM**。被杀进程属于容器侧（宿主 uid 1000），虚拟内存 12.4 GB，
常驻约 4 GB，明显不是启动栈的一部分（当时没有 YOLO 进程，网关/相机节点常驻都在
200 MB 以下）。它的身份没有查清：journal 里只有 `Name: python3`，没有 cmdline，
该进程也没有向 journald 输出过内容。

**为什么 OOM 会演变成“只能断电”**（按证据强弱排序）：

1. **sshd 被限流**（证据：`MaxStartups throttling`）。内存压力下新连接完成不了
   banner 交换，远程维护入口消失。
2. **网关 socket 只接不应**（观测：TCP 22 与 8765 都能建连，但 8765 永不应答）。
   推测是同一轮内存/调度饥饿让 Python 网关线程无法运行；这一点没有在事故中直接
   测量，标为假设。
3. **没有硬件看门狗**：用户态再也不会自己恢复，只能断电。
4. **关键单元没有重启策略**：`armpi-gateway-pose`、`start_node` 都是 `Restart=no`，
   即使内核撑过去，服务也不会自己回来。
5. **启动期错误被忽略**：`armpi-vision` 失败只出现在 journal 里；重复的
   `/swapfile` 条目每次启动都让 fstab generator 失败。

## 4. 为什么监控没发现

操作员侧的检查全是网络层：`ping` 正常、端口能连。事故中唯一可靠的应用层信号是
**SSH banner** 和**网关 `/health` 的响应体**，两者都失效了，但没人轮询它们。

## 5. 同时发生的 Studio 故障（人为放大）

`tools/studio/start_studio.sh` 当时的顺序是：

1. 检查 8000 端口，**杀掉占用者**；
2. 再去机器人上取网关 token（SSH）；
3. 取不到就退出。

机器人不可达时，第 2 步失败，但第 1 步已经把健康的 Studio 后端杀掉了。结果
是“机器人坏了，Studio 也一起没了”。已在 `jcheng-manipulation` 修正为
**先预检、后动端口**；Studio 看护也内置了“网关不可达时不杀后端”的规则。

## 7. 未解问题

- 4 GB `python3` 的身份。下一次内存回落时，巡检会记录 top 3 常驻进程。
- 看门狗尚未在真实卡死中触发过（装机当天没有复现），需要一次受控的
  “systemd 停止喂狗”测试或等待下一次真实事件；两者都要在机械臂静止时进行。
- 8765 挂死的确切原因（线程饥饿 vs. 内存分配失败）只有推断，没有栈或采样。

## 8. 教训

1. **健康检查要探应用层**：端口在听不等于服务在回。
2. **远程入口要受保护**：OOM 时先死的不能是 sshd。
3. **自动恢复要有层次**：进程级重启 → 服务级重启 → 整板重启，逐级兜底。
4. **运维脚本失败时不能扩大故障**：任何“先杀后验”的顺序都要反过来。
5. **卡死时的自动动作要尊重运动状态**：能重启，但要知道机械臂在不在动。
